# Orchestrator: pitfalls that have already cost time

Read **only by the Producer**. The entries about the orchestrator itself port to any project as they are; where build commands are mentioned, substitute `$GATES_CMD` and its neighbours from `.studio/project.conf`. The specific file names belong to the pilot project and serve as evidence, not as a template.



- Gates means ALL of them (`$GATES_CMD`), not one test run: git does not show a semantic divergence between two tasks.
- Gates after every merge, including "docs only" and "assets only":
- A branch whose base is older than trunk brings stale ENTRIES, not breakage. Before
- Land branches in ascending order of their base.
- High load is the question "whose load is it and how old is it", not a verdict.
- Whoever demands a quiet machine must provide one: on 11 August two workers sat in wait loops for a threshold that my own wave of six workers never allowed. They were waiting not for the condition but for me.
- For a timeout defect, high load is a required condition, not an obstacle: a green series under load 90 proves more than one under load 5, and a red one under it is uninformative.
- An idle window is not an idle machine: a worker on Haiku burns the same cores as one on Opus. A wave is widened by cores, not by token windows.
- A worker can be launched and NOT STARTED: the spec hangs in the input field unsent ("[Pasted text …]" next to the agent banner). The sign: zero commits AND zero edited files AND the banner in the terminal tail; cured by `terminal send --enter --text ""`. On 11 August `ui-three-bugs` stood like that for three hours and the framing worker for two. It must be checked in the first minutes after handing out, not writing the `+0` off to dependency installation.
- An empty `task-create` response is most often a detached Run, not a bad spec: `worker-start` then lies with "Missing required --task". Cured by `orca orchestration run-use --id <run>`; the flag is `--id`, not `--run`.
- Never print terminal handles truncated: on 11 August I reconstructed the end of a handle from memory and got `terminal_handle_stale`, that is "no such handle", and nearly declared a live worker dead. A handle is either whole or not printed.
- A worker picks up messages at a turn boundary, not immediately: changing the order of work on the fly is unreliable. The order goes in the spec before launch; afterwards only what will not lose its meaning by arriving late is sent.
- "The clock is running but the tokens stand still" is a suspicion, not a verdict: it is checked by a keypress, and on 11 August the worker turned out to be alive.
- A trunk freeze is calibrated to the price of the gates: at 257 s it is justified, at 53 s six cycles of silence cost more than one re-merge.
- `worker-start` on a hand-made worktree: `--name`, `--display-name`, `--base-branch`, `--setup` are CREATION flags and are rejected for an existing one; put the path under `orca/workspaces/<branch>`, otherwise `selector_not_found`.
- A worker idle at the prompt burns no tokens but holds an irreplaceable provider: give the free one the blocking work rather than starting a seventh.
- `selector_not_found` on a fresh worktree: Orca has not walked it yet: `orca worktree list` forces a rescan, after which `worker-start` goes through.
- A gate measurement and a merge are two workers running the same gates: putting them in one cycle means they measure each other.
- Load under a wave is the neighbours' gate runs, not background: eight worktrees each running its own `$GATES_CMD`, each with its own pool of processes and browsers. Gate non-determinism is a concurrency problem, not only a ceilings problem.
- The sign of "launched and not started" is the welcome banner in the terminal tail; verified in both directions on one worker. `latest cursor` is no good for this: it counts pages, not lines, and for a working claude worker stays at 1: it gave 4 false results out of 4.
- Pressing Enter for a new worker is part of setting the task, not a cure: four cases out of ten launches in a day. The instrument catches it after half a minute, but EVERY launch must be checked.
- Load 203 on 12 cores is NOT "nine workers" but TWO concurrent gate runs: the eleven top processes by CPU belonged to two worktrees. Count the wave by gate runs, not by the number of workers.
- A merge message "into main" does not prove the commit is on trunk: check `git log main..<branch>` and `git rev-parse --abbrev-ref HEAD` BEFORE merging. Twice in the project a merge went into the branch whose worktree it was launched from.
- A directive that must be carried out goes into a message ALONE and without questions: the worker takes the last thing, and an analysis at the end of the letter replaces the action. Three times in a row I got bookkeeping instead of a merge.
- Having compressed a letter down to one directive, I crossed out the CHECK along with the questions, and trunk landed red. One directive per letter is right, but the condition "do not land if the gates are red" is part of the directive, not a question.
- `selector_not_found` with an existing, registered worktree is about the TASK, not the worktree: the Run has detached; cured by `orca orchestration run-use --id <run>`. Same root as the empty `task-create`.
- A review branch is removed as soon as its findings are handed to the authors: the report does not go to trunk (§1); the finding lives in the fix, the card and the rule. Otherwise the "work without a worker" instrument drowns in reports nobody is waiting for.
- In `worker-list` the field `resource.worktreeId` of ALL workers points to the project root, not to the worktree that was passed: it cannot tell you what a worker is busy with. The sign "branch in progress" is taken from `git worktree list`, not from Orca.
- A task carries a DIRECTIVE, not a link to a file with the directive. "Read such-and-such file with the plan": three workers out of four carried it out literally: read it, retold the plan in the report and delivered `worker_done` with a clean tree. The fourth did the work: its task said "this is a ready-made solution, execute it" plus the branch and `npm ci`. The task text must carry a verb, a branch and a direct "the work is not done if there are no commits of your own".
- `orchestration reply` is invisible for unsolicited letters, but for a BLOCKING `ask` it is precisely the reply channel: the worker received the verdict and continued work at once. Distinguish by whether the worker is waiting, not by the command name.
- The spec retells the card in its own words and inverts the defect. "The route is visible over the HUD" described the wrong failure: the panels do not capture the pointer, rather than being drawn over the route. The worker asked and was right; the card has the authority, and on divergence the spec is corrected.
- If Enter does not change the tail, the spec was NOT delivered at all rather than hanging in the input field: there is nothing to press. Cured by sending the directive itself as text (`terminal send --enter --text "<instruction>"`), and the sign of success is "Working" appearing, not the fact that bytes were sent.
- The banner in the tail also stands for a worker that has FINISHED: having delivered, it returns to the prompt. What distinguishes them is not the banner but the traces of work above it (`Ran …`); the cures are opposite: Enter for one, collecting the work for the other.
- The spec fails to reach the worker in roughly every third launch, and both such failures in a row hit ONE worktree (`ui-three-bugs`): a hypothesis about reusing a worktree with an already finished worker, not a rule. The sign: the input field shows the default hint ("Run /review on my current changes") instead of the spec. Cured by sending the instruction as text.
- Measure the spend rate over the WHOLE current window (the monotonic tail of the `used` ledger), not against a receding base of 0.3…1.4 h: with the provider's granularity of 1 pp, one quantisation step over a short baseline gives a spread of several times. The instrument printed ×16.1 for one window where the remainder had shifted by exactly one, and on top of that compared numbers across a window reset boundary.
- Only the Producer merges into trunk, and that is not a preference but a git constraint: `main` is checked out in the coordinator's worktree, and another worker cannot switch to a busy branch. The Integrator role was therefore an extra handoff and was removed on 11 August (§4 of `STUDIO.md`).
- `400 Claude Code X does not support this model; version Y or newer is required` is the `claude` binary on PATH lagging behind the model, not the model being withdrawn; the worker is marked `dispatched` and looks alive. `claude update`, then repeat the launch, rather than moving the role (`agents.md`, measured on this machine on 24 September 2026).
- After `git worktree add` Orca registers the worktree with a delay: the first `worker-start` answers `selector_not_found`, the second goes through. Do not create the worktree again: repeat the launch.
- In the landing spec the gates are run BEFORE the merge into trunk: first merge trunk INTO the task branch and run `$GATES_CMD` there, then move trunk. Otherwise "gates red: leave trunk as it was" cannot be met: the merge is already in.
- Worktrees inside the project must be excluded from EVERY gate: `.worktrees/**` in `eslint.config.js`. The landing of 11 August failed on 12 lint errors, none of which belonged to trunk.
- Take the task for `worker-start` by the id from the `task-create` response, not by searching for `display_name`: names repeat across run generations, and a match gives `selector_not_found` on a seemingly live task.
- The sign of a live claude worker is not `Working` but `⏺` / `Noodling…` / `esc to interrupt` / a token counter; checking by other words gives "UNCLEAR" on a healthy worker and provokes a needless Enter.
- The sign of "the worker is working" is not terminal output (the spinner redraws itself) but the AGE OF THE LAST EDIT across the whole worktree (the command is in the "Cycle" section of `START_PROMPT.md`). The form `-newermt "-15 minutes"` fails here (`bfs`, not GNU find) and under `2>/dev/null` reads as death; counting "files newer than 15 minutes" in a worktree younger than 15 minutes gives 422 and cannot tell liveness from `git worktree add`.
- **Assemble the body of a letter to a worker in a file and pass it as `--body "$(cat file)"`.** Backticks inside double quotes are EXECUTED by the shell: on 11 August my letter with a capture command in backticks started a build right in trunk, and the name of a guard vanished from the text: the worker got an instruction with holes. The `$(cat …)` substitution is not parsed a second time and is therefore safe.
- A worker with `% until auto-compact` in the tail and uncommitted work is an emergency: commit its worktree yourself immediately, without waiting for the report. On 11 August 30 files hung like that for an hour and a half at 3 % before compaction.
- A shell `wait` on background runs hangs the worker dead: forbid `&` with `wait` in the spec, require sequential launch or a timeout.
- Small text on a ×1 screenshot is NOT readable by eye, and that is my mistake, not nitpicking: on 11 August I read `tomorrow +500` in the resources panel as the Russian "завтра +500", went into both locales, into `setText` and into the bundles, and was about to file a card about an untranslated string. On the ×3 screenshot the same string reads unambiguously and in English. A font at 640×360 gives about five pixels per glyph, and Cyrillic and Latin are indistinguishable in it. The rule: a claim about TEXT on a screenshot is made from the ×3 step, and if there is none, demand it from the worker rather than guessing. A side benefit of that trip: ×3 showed `Week_1` and the debug token `--debug-border` on 53 map rules; both findings have no observable effect and did not go into cards.
- A bare prompt in the `worker-read` tail does NOT prove "launched and not started": on 11 August two claude workers showed an empty prompt while `orca terminal list` in the same second printed for them a derived task title ("Remove ambience, balance audio levels across screens") and the spinner `Deciphering…`. The tail returns a stale slice. Judge BY `terminal list`: a derived title instead of the task name + a spinner = the worker has read the spec and is working. A needless Enter into a working agent goes in as an empty message and knocks it off course.
- `selector_not_found` on a fresh worktree is cured not by one retry but by SEVERAL: on 11 August the launch went through on the FOURTH attempt within two minutes, while `orca worktree list` was already printing the worktree under that very selector and the task sat in the `ready` state. So both "readiness signs" lie until the registration settles. Recreate neither the worktree nor the task: repeat the launch.
- The age of file edits is blind to a worker running BROWSER tests: on 11 August `play-route-stall` showed "31 minutes without edits" with a clean tree and a ready commit, while in the tail at that very second `ATTEMPT 3` was running with output from 4.7 s ago. It was checking the game with inline scripts through an already running session and wrote NOTHING to the worktree. The sign "the playtester is alive" is the tail, not the files; files are fine for a worker that edits code. This is the second false "worker has stalled" in a day from the same instrument (the first was `-newermt` on bfs), hence: for QA roles the tail first, and only then the files.
- `git worktree remove` does NOT kill the dev server the worker brought up: on 11 August, after removing four playtest worktrees, four processes remained (two servers and their two companions): half an hour old each, 0 % CPU, but with busy ports and in the load list. That same class already cost me a false trail: someone else's preview server from an ABANDONED environment sat for 18 hours on exactly the port that screenshot capture asks for. Clean up explicitly after removing a worktree: `ps -Ao pid,args | grep worktrees/<name>` and `kill`. Otherwise they accumulate and lie in load attribution: a process of a worktree that no longer exists reads as a live neighbour.
- A blocking question is answered ONLY through `orchestration reply --id <msg>`, not by a `send` letter: on 11 August I sent a detailed answer by `send`, the worker did not see it, and the question came again the next cycle: the worker had been standing idle all that time. The sign of the mistake is exactly that: the same `question` in the mail on the next cycle. `send` is not a channel for a blocking `ask`, even if the letter was delivered.
